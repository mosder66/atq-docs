# API 通信协议基础规范

本指南详细说明了与本系统 API 进行安全通信的基础协议，包括通用请求响应格式、数据加密机制及签名核验算法。

## 1. 通用请求规范

API 采用 **HTTP POST** 方法进行交互，请求体格式为 **JSON**。

### 1.1 标准请求体格式

```json
{
  "app_id": "1001",
  "time": "1708420000",
  "data": "业务数据（原文或加密后的字符串）",
  "sign": "3a2b3c4d5e6f..."
}
```

| 字段       | 类型          | 是否必须 | 说明                                                                |
| :--------- | :------------ | :------- | :------------------------------------------------------------------ |
| **app_id** | String/Int    | 是       | 应用分配的唯一标识。                                                |
| **time**   | String/Long   | 是       | 客户端请求时的 Unix 时间戳（秒）。系统默认有效期为请求前后 300 秒。 |
| **data**   | Object/String | 是       | 业务参数数据。若开启加密，则必须为加密后的 Base64 字符串。          |
| **sign**   | String        | 建议     | 请求签名，用于防篡改。具体算法见下文。                              |

---

## 2. 签名计算 (Signature)

系统采用 **HMAC-SHA256** 算法进行签名校验，确保请求来源的真实性及数据完整性。

### 2.1 签名计算公式

待签名字符串 **(SignData)** = `app_id` + `time` + `dataStr`

> **注意**：`dataStr` 如果是 JSON 对象，需先序列化为紧凑格式的字符串；如果是加密后的字符串，则直接参与拼接。

### 2.2 计算步骤示例

假设：

- `app_id` = "1001"
- `time` = "1708420000"
- `data` (JSON 内容) = `{"card":"TEST-CARD"}`
- `secret_key` = "MyTopSecretKey"

1. **构造投影字符串**: `"10011708420000{"card":"TEST-CARD"}"`
2. **计算算法**: `HMAC-SHA256(SignData, SecretKey)`
3. **输出结果**: 得到 64 位十六进制小写字符串即为 `sign`。

## 3. 数据加密 (Encryption)

### 3.1 加密模式表

| 类型码 | 映射方法         | 说明                                                             |
| :----- | :--------------- | :--------------------------------------------------------------- |
| **0**  | 明文 (Plaintext) | Data 字段直接提交 JSON 对象或 JSON 字符串。                      |
| **1**  | **RC4**          | 使用 `secret_key` 作为 Key 开展 RC4 对称加密。                   |
| **2**  | **Base64**       | 仅对明文 JSON 字符串进行 Base64 编码（低安全性，仅防肉眼）。     |
| **3**  | **AES-256-ECB**  | 使用 `secret_key` 进行 AES 加密，填充方式通常为 `PKCS5Padding`。 |
| **4**  | **DES-ECB**      | 使用 `secret_key` 进行 DES 加密。                                |

### 3.2 加密流程示例 (以 AES 为例)

1. 将业务 Map `{"user_id": 1}` 序列化为 `{"user_id":1}`。
2. 使用 `secret_key` 对该字符串进行加密。
3. 将加密结果转为 **Base64** 编码的字符串。
4. 将该字符串填入请求体的 `data` 字段。

## 4. 响应规范

所有响应均为 JSON 格式，结构如下：

```json
{
  "code": "200",
  "message": "success",
  "data": "响应业务数据（可能经过加密）",
  "timestamp": "1708420005",
  "sign": "..."
}
```

### 4.1 响应签名校验 (客户端可选)

待签名字符串 = `timestamp` + `code` + `message` + `dataJson`

> 其中 `dataJson` 是返回体中 `data` 字段的 JSON 表现形式。

## 5. 错误代码参考

| 代码    | 描述       | 常见原因                                                   |
| :------ | :--------- | :--------------------------------------------------------- |
| **400** | 客户端错误 | 签名不匹配、请求时间过期、缺少必要公共参数、数据解析失败。 |
| **401** | 未授权     | 登录已过期、卡密已失效或被封禁。                           |
| **403** | 禁止访问   | 非法 IP 段、多设备在线受限。                               |
| **500** | 服务器错误 | 服务器内部逻辑执行失败。                                   |
